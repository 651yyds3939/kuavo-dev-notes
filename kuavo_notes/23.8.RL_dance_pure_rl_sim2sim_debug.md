## 二、修复清单（共 8 处）

### 2.1 play.py（训练侧导出，2 处）

**文件**：`scripts/rsl_rl/play.py`

#### Bug 1：S46 的 gym2lab/lab2gym 映射被用于 S49

- **位置**：`_OnnxPolicyExporter.__init__` 第 94-95 行
- **根因**：S46 的硬件关节序是按类型交替的（`leg_l1, leg_r1, zarm_l1, zarm_r1, leg_l2, ...`）。S49 的 `mujoco_node.cc` 通过 `kRlJointNames` 直接用 Lab 序（`leg_l1..l6, leg_r1..r6, zarm_l1..l7, zarm_r1..r7`）。ONNX 导出时用 S46 映射重排了 S49 的数据。
- **修复**：gym2lab 和 lab2gym 改为恒等映射 `list(range(26))`

#### Bug 2：referenceJointPos 被错误重排

- **位置**：`_reorder_joint_blocks_gym_to_lab` 第 98-103 行
- **根因**：C++ 端的 `danceReferenceTrajectoryGym_` 已经是 Lab 序。但 ONNX forward 对所有 26 维块（offset 9/35/61/87）统一做了 gym2lab 重排，把 Lab 序的 referenceJointPos 搅碎了。
- **修复**：只对 action（offset 87）做重排。jointPos、jointVel、referenceJointPos 都是 Lab 序，不需要重排。

### 2.2 humanoidController.cpp（部署侧控制器，5 处）

**文件**：`kuavo-rl-opensource/kuavo-robot-deploy/src/humanoid-control/humanoid_controllers/src/humanoidController.cpp`

#### Bug 3：观测 jointPos 用了 C++ 站姿基准而非训练 URDF 零基准

- **位置**：第 704、1885-1888 行
- **根因**：训练时 Isaac 的 `joint_pos_rel = sensor - asset_default`；S49 lite 训练资产默认角为 0，所以出生站姿的膝观测应约为 `+0.52`。C++ 原先计算 `sensor - defalutJointPos_`，把同一膝观测变成 0。
- **修复**：`sim_joint_obs_offset_ = -defalutJointPos_` 抵消减法，使 `jointPos = sensor`（绝对角）。

#### Bug 4：referenceJointPos 基准不一致

- **位置**：第 1920 行
- **根因**：`danceReferenceTrajectoryGym_` 是 CSV 减去 C++ 站姿（`CSV - defalutJointPos_`），训练用的是 CSV 减去 0。膝 reference 在 C++ 中=0，训练中=0.52。
- **修复**：`rl_from_start` 时 `referenceJointPos_ += defalutJointPos_`，恢复为绝对角。

#### Bug 5：action→q_des 的基准不一致

- **位置**：第 1527-1528 行
- **根因**：训练时 `q_des = action × 0.30 + 0`。C++ 中 `q_des = action × 0.30 + defalutJointPos_`（膝 0.52）。网络输出 action=1.73 表示"膝目标=0.52"，但 C++ 算成 `1.73×0.30+0.52=1.04`。
- **修复**：`rl_from_start` 且非沉降阶段时，不加 `defalutJointPos_`。

#### Bug 5b：沉降阶段 PD 目标为 0

- **位置**：同上
- **根因**：RL 推理前有沉降阶段让物理稳定。`action=0`，基准为 0 → `q_des=0`，PD 把膝从 0.52 推到 0。
- **修复**：沉降阶段保持 `defalutJointPos_` 作为基准。

#### Bug 6：sagittal 腿关节轴符号翻转

- **位置**：第 1889、1534 行
- **根因**：Isaac URDF→USD 转换时，6 个 sagittal 面腿关节（髋俯仰/膝/踝，左右各 3）的轴方向与 MuJoCo 原始 URDF 相反。观测中膝=-0.52 而非 +0.52。
- **修复**：观测（jointPos/jointVel）和动作（q_des）两端都对索引 [2,3,4,8,9,10] 做符号翻转。

### 2.3 mujoco_node.cc（部署侧 MuJoCo 节点，2 处）

**文件**：`kuavo-rl-opensource/kuavo-robot-deploy/src/mujoco/src/mujoco_node.cc`

#### Bug 7：首帧命令到达前 PD 无目标

- **位置**：第 705 行
- **根因**：`pending_joint_cmd` 为空 → `q_des = q`（当前位置）→ PD 误差为零 → 零力矩。出生后前几个物理步完全不受控。
- **修复**：fallback 从 `q` 改为 `qpos_init[qa]`（spawn 姿态）。

#### Bug 8：首帧命令未启用 RL-native PD 路径

- **位置**：第 1200 行后
- **根因**：`pending_joint_cmd.use_rl_native_pd` 默认为 false。首帧走老路径，用顺序索引 `qpos[7+i]` 读关节——S49 的 qpos 混了手指，读到错关节。
- **修复**：qpos_init 加载后，预填充 `pending_joint_cmd`，`use_rl_native_pd=true`，站姿为初始目标。

## 三、调试方法

### 3.1 核心工具

**`analyze_r_takeover_bag.py`**：位于部署仓根目录。读取 rosbag 中 `/rl_controller/singleInputData`，解析 115 维观测各块并打印首帧。

```bash
# MuJoCo 启动后立刻录音帧观测
rosbag record -O debug.bag /rl_controller/singleInputData /rl_controller/actions
# Ctrl+C 停止后分析
python3 analyze_r_takeover_bag.py debug.bag
```

### 3.2 健康判据（纯 RL 模式首帧）

| 指标 | 健康值 | 异常信号 |
|------|--------|---------|
| `gravity_body[2]` | ≈ -0.999 | > -0.95 → 已明显倾斜 |
| `jointPos[3]`（左膝） | ≈ 0.52 | 负值 → 符号翻转 / 已倒下 |
| `jointPos[4]`（左踝） | ≈ -0.30 | 正值 → 符号翻转 |
| `referenceJointPos[3]` | 0.52 | 0 → 基准未修复 |
| `action max` | < 3.0 | >7.0 → 观测错导致网络输出饱和 |
| `jointVel max` | < 2.0 | >10 → 已高速崩塌 |

### 3.3 代码中的关键日志

```text
[RL mode] rl_from_start spawn: obs offset = -defaultJointPos (training URDF zero ref)
[RL mode] RL from start: inference on after settle, full policy, no ramp
[mujoco_node] Pre-loaded pending_joint_cmd from qpos_init (RL native PD hold)
[RL mode] First RL inference step: max|action|=X.XXXX
```

- `max|action|` < 1.0 且稳定 → 观测链路正常
- `max|action|` = 8.0（截断值）→ 观测或符号有误

### 4.2 残余问题：Isaac PhysX vs MuJoCo 物理本征差异

观测链路对齐后，机器人仍会从站姿缓慢前倾。当前优先假设是 **WBC→RL 接管首帧的目标力矩不连续**，其次才是 PhysX/MuJoCo 的接触、阻尼、执行器和模型差异。仅凭相同 `q_des` 在两个引擎中表现不同，不能提前断言“无法通过调参改善”；必须先完成 hold-seed 和 seed-to-policy 两组对照。

- **Hybrid WBC+RL**（`sim_keep_wbc_with_rl:=true`）：WBC 负责站姿，RL 专注手臂。观测链路修复后，手臂表现应显著改善。

## 五、关键教训

1. **Sim2Sim 对齐不是"调一个参数"，是一个一个 Bug 修出来的。** 8 处 Bug 分布在训练侧导出、部署侧控制器、部署侧物理节点三个文件中，每处都独立导致劈叉。

2. **不要用中间值"折中"——精确对齐才能 work。** 本项目的 bug 包括：符号翻转、基准偏移（站姿 vs 零位）、索引映射错误。没有一处是"权重调整"能解决的。

3. **rosbag + 逐帧分析是唯一的调试方法。** 看到 `action=±8.0` → 网络在输出垃圾 → 输入观测有问题。看到 `jointPos` 符号反转 → 传感器/转换层有 bug。没有 bag 数据就是盲目猜测。

4. **S49 和 S46 的硬件关节序不同。** S46 的 play.py 映射对 S49 是错的。同一份 mujoco_node.cc 里 S49 用 Lab 序（named sensor map），S46 可能是顺序索引——改任何一处都要验证对两个版本的影响。

5. **物理引擎差异是真实存在的，但必须最后定性。** 8 处软件 Bug 修复后劈叉消失、只剩缓慢前倾；当前先用 WBC 等效 seed 区分交接跳变、纯 PD 平衡点和 ONNX 闭环，完成这些对照后才评估 PhysX/MuJoCo 参数差异。

## 六、WBC 等效 seed action 接管（最新补充）

### 6.1 为什么 zero-action 实验不够

`sim_rl_debug_zero_action=true` 会让 action 变为 0，对 v18 纯 RL 来说相当于把 PD 目标直接放到默认基准。该实验仍前倒，只能说明“零 action 不是 MuJoCo 中的静态平衡点”；它没有复现交接前 WBC 正在输出的支撑力矩，因此不能判断是 ONNX 策略、纯 PD 平衡点还是接管跳变导致倒地。

### 6.2 seed action 的实际公式

交接前记录最后一帧 WBC 力矩 `tau_wbc` 和当前关节状态 `q, qdot`。RL native PD 满足：

`tau = Kp * (q_des - q) - Kd * qdot`

所以先反解出与 WBC 力矩等效的目标角：

`q_des_seed = q + (tau_wbc + Kd * qdot) / Kp`

再按 v18 的 action 定义反解 seed：

`action_seed = (q_des_seed - rlPdTargetJoint(i)) / (actionScale * actionScaleTest[i])`

这里的 `rlPdTargetJoint(i)` 是当前纯 RL 路径使用的目标基准；实现还会把 seed clip 到 `[-clipActions, +clipActions]`。必须复用相同的关节顺序、sagittal 符号、目标基准和缩放，撤掉 WBC 的第一帧，RL native PD 才会理论上输出接近交接前的关节力矩。

### 6.3 新增参数与实验顺序

| 参数 | 默认值 | 用途 |
| --- | --- | --- |
| `sim_rl_use_wbc_seed` | `true` | 启用 WBC 力矩反解 seed |
| `sim_rl_seed_blend_sec` | `2.0` | seed 平滑过渡到 ONNX action 的时间 |
| `sim_rl_debug_hold_seed_action` | `false` | 一直保持 seed，不进入 ONNX，用于验证纯 PD 平衡点 |
| `sim_rl_debug_zero_action` | `false` | 强制零 action；seed 也会被清零，只保留旧对照语义 |
| `sim_rl_spawn_pitch_rad` | `0.0` | pure-RL spawn pitch；不再默认带前倾偏置 |

实验解释：

1. **纯 WBC** 能站：模型和 WBC 对照成立。
2. **hold seed** 能站：撤掉 WBC 后，RL native PD 可以维持等效支撑；若此时倒，先查 PD/clip/符号/物理参数，不进入 ONNX。
3. **seed → policy** 才倒：重点查 ONNX action、相位、history 和策略在 MuJoCo 域内的闭环稳定性。
4. **zero action** 倒但 hold seed 不倒：证明默认零 action 不是平衡点，也证明 seed 交接有实际价值。

### 6.4 当前边界

这套 seed 解决的是 **控制器交接连续性**，不等同于让 WBC 永久参与。blend 结束后仍是纯 RL PD。若 hold-seed 稳定而完整策略失稳，后续才进入策略域随机化、PD 参数和 MuJoCo 物理对齐；若 hold-seed 本身不稳，应先解决执行器等效性，继续改奖励函数没有针对性。
