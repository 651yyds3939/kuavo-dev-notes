### 10.2 v15 到 v18 的关键方向变化

1. **从全身 CSV 改为 arms-only**：腿部 CSV 奖励权重归零，手臂继续跟 14 维 CSV；目标变成“腿允许平衡微调，但不跳舞”。
2. **从负向硬腿锁改为正向站姿吸引子**：`joint_deviation_legs` 从强 L1 惩罚转为 `track_leg_standing_upright_exp`。前者告诉策略“不要动”，后者告诉策略“站到哪里能持续拿分”。
3. **观测与奖励统一**：v16 的 observation 给移动腿 CSV、reward 要固定腿，是同一时刻两个目标。v17 的 `reference_joint_pos_rel_arms_csv_legs_standing` 把前 12 维固定为自然屈膝站姿，只让后 14 维随 CSV 动。
4. **脚踝单独建模**：整腿 12 关节均方误差会稀释两个踝 pitch 的错误，所以增加 `track_ankle_pitch_standing_exp` 和带死区的软惩罚。
5. **v18 针对“小碎步”而不是继续锁腿**：直接惩罚脚 link 速度、持续离地和接触滑动，保留腿关节低频平衡能力。

## 第十一章：奖励函数作用、读数和调参方向

奖励的实际值通常是“函数输出 × weight”，TensorBoard 的 `Episode_Reward/*` 又是 episode 内累计后的统计。不要把不同项的绝对数直接当成同一量纲；先看趋势、符号、对应视频现象，再比较同一 tag 在不同 run 的变化。

### 11.1 模仿与站姿正奖励

| 配置项 / 函数 | 实际计算与作用 | 视频里解决什么 | 调参风险 |
| --- | --- | --- | --- |
| `track_punch_arms` / `track_punch_arms_trajectory_upright_exp` | 对 14 个手臂关节与当前 CSV 帧做均方误差，再算 `exp(-error/std²)`，最后乘 upright gate | 手臂幅度、节奏和姿态跟随 | weight 太大时策略牺牲站立追手；`std` 太小或门控太严时早期几乎拿不到梯度 |
| `track_punch_legs` | 对 12 个腿关节跟踪移动 CSV | 历史全身舞的腿部编舞 | arms-only 中必须为 0，否则和固定站姿目标冲突 |
| `track_leg_standing` / `track_leg_standing_upright_exp` | 腿对固定屈膝站姿做指数跟踪并乘站立门控 | 防跪、防直腿、允许围绕自然站姿小幅平衡 | `std` 太小会近似硬锁；权重太低又不能形成稳定吸引子 |
| `track_ankle_pitch_standing` | 只看左右 `leg_*5_joint`，把踝 pitch 拉向约 `-0.30 rad` | 修复只靠脚跟支撑的“勾脚”捷径 | 不能替代整腿站姿；过窄会压掉正常踝平衡动作 |
| `reference_joint_pos_rel_arms_csv_legs_standing` | 这不是 reward，而是 policy observation；腿 12 维固定站姿、臂 14 维来自 CSV | 消除 v16 的输入目标冲突 | 部署端必须保持同样 26 维顺序、基准和相位 |

`std` 的方向必须记清：变小代表跟踪核更尖、更严格；变大代表容错更宽。严格不总是更好，策略早期离目标较远时，过小 `std` 会让正奖励接近零。

### 11.2 躯干稳定与原地约束

| 配置项 | 作用 | 对应现象 | 实际经验 |
| --- | --- | --- | --- |
| `flat_orientation_l2` | 惩罚躯干投影重力的水平分量 | 前后倾、侧倾 | v2/v17/v18 的 `-12` 是门控型手臂奖励能够工作的稳定底座；`-2/-5` 多次不够 |
| `base_height` | 惩罚 base 高度偏离 `0.87 m` | 下蹲、弹跳、低姿态刷分 | 与 `penalty_root_squat` 分工：一个管连续偏差，一个管跌破红线 |
| `penalty_root_squat` | 只惩罚低于 `0.72 m` 的部分 | 跪着跳舞 | v1.5 缺它时出现典型跪姿局部最优 |
| `termination_penalty` | episode 因终止条件结束时给大负值 | 快速倒地、非法姿态 | 只能提高倒地成本，不能替代可学习的连续站立奖励 |
| `base_lin_vel_xy_stationary` | 惩罚机身坐标系下 XY 速度平方 | 边跳边后退、横向漂移 | 只管“正在动多快”，不能保证长期回到出生点 |
| `penalty_root_xy_displacement` | 惩罚 root 相对 `env_origin` 的 XY 位移平方 | 慢慢走远 | v7 的 `-3` 能拉回原点但可能过强；v17/v18 用 `-0.5` 温和锚定 |
| `base_ang_vel_yaw_stationary` | 惩罚 root yaw 角速度 | 原地自转 | CSV 本身 yaw 小时有效；不要与需要转身的舞蹈共用 |
| `lin_vel_z_l2` / `ang_vel_xy_l2` | 抑制垂直弹跳和 roll/pitch 角速度 | 上下抖、躯干晃 | 作为弱正则，不应盖过 mimic |

### 11.3 动作、腿部和平滑正则

| 配置项 | 作用 | 视频/TensorBoard 诊断 | 调参经验 |
| --- | --- | --- | --- |
| `action_rate_l2` | 惩罚相邻 action 差值 | 高频抽动、指令跳变 | v8 的 `-0.12` 虽止抖但会压缩手臂；v18 回到 `-0.006` |
| `action_smoothness_l2` | 惩罚 action 二阶差分 | 速度连续但加速度突变的抖动 | 与 action rate 一起加太重会让动作幅度小、跟不上相位 |
| `penalty_leg_joint_vel_l2` | 只惩罚 12 个腿关节速度平方 | 腿高频颤抖 | 比全局 action 正则更精确，不会过度压制手臂 |
| `penalty_leg_joint_acc_l2` | 只惩罚腿关节加速度平方 | 细碎震颤和力矩尖峰 | 数值天然很大，权重应在 `1e-7` 量级逐步调 |
| `joint_deviation_hip` | 轻度约束髋 roll/yaw 偏离默认姿态 | 双腿外撇、扭髋换稳定 | 只能微约束；过大会阻止横向平衡 |
| `dof_acc_l2` / `dof_power_l2` / `dof_torques_l2` | 全局加速度、功率、力矩正则 | 能耗高、动作粗暴 | 它们负责“代价”，不能承担具体行为目标 |
| `dof_pos_limits` | 接近或越过关节限位时惩罚 | 反关节、大幅扭曲 | 属于安全边界，不用于塑造正常舞姿 |

### 11.4 脚部接触奖励

| 配置项 | 作用 | 成功/失败经验 |
| --- | --- | --- |
| `feet_slide` | 脚接触地面时惩罚脚平面速度 | v18 用于消除接触状态下的小滑步；只在接触时生效 |
| `penalty_feet_motion_l2` | 惩罚双脚 link 三维线速度平方 | 直接针对“小碎步”和脚在空中乱动；比硬腿锁更符合任务目标 |
| `penalty_feet_airborne` | 脚离地超过 `grace_time=0.04s` 后累计惩罚 | 允许接触传感器短暂抖动，但抑制真正换脚 |
| `penalty_ankle_pitch_standing_soft` | 踝目标外 `0.08 rad` 死区后才二次惩罚 | 小平衡动作不罚，大幅勾脚才罚；比刚体 foot-flat 温和 |
| `penalty_foot_pitch_deviation` | 历史方案：踝 pitch 跟 CSV | v8 太轻无效；加重后会与接触和站立目标冲突，v18 不再使用 |
| `penalty_foot_link_flat_l2` | 历史方案：接触时直接要求脚 link +Z 对齐世界 +Z | v9/v14 出现出生即倒或高频震颤；不是当前方案 |
| `feet_contact_force_velocity` | 历史方案：惩罚接触力×脚速度超过阈值 | 与其他脚约束叠加后梯度过猛；v9 失败后关闭 |
| `contact_force` | 超过阈值的足底接触力惩罚 | 防止砸地和冲击峰值；不是“必须保持接触”的奖励 |
| `undesired_contacts` | 腿非脚部、base、手臂等不该碰地的 link 接触即罚 | 防止跪地、撑地、躺地刷 mimic | body name 与碰撞模型必须匹配，否则可能漏罚或误罚 |

### 11.5 为什么“正向站姿奖励”优于“负向腿锁”

v15 的 `joint_deviation_legs=-5` 是无界负反馈：任何腿部调整都扣分，包括救命的平衡调整。策略很容易在“保持腿角不变”和“防止倒地”之间僵住。

v17/v18 的 `track_leg_standing` 是 `[0, 1]` 范围的正反馈，并带 upright/height gate：机器人只有站得好、腿接近自然姿态时才能持续拿分。它既给出明确目标，又允许在目标附近做连续微调。这是从 v15 到 v17 能稳定的核心，不只是一次权重微调。

## 第十二章：实际如何看视频、TensorBoard 和 RUN_CONFIG 调参

### 12.1 三种证据各自负责什么

| 证据 | 能回答的问题 | 不能单独回答的问题 |
| --- | --- | --- |
| `play.py --video` 或交互回放 | 是站、跪、倒、勾脚、碎步、后退还是手臂不动；动作是否自然 | 为什么发生；奖励项在训练中何时恶化 |
| TensorBoard | 哪个阶段开始崩、奖励是否仍学习、终止是否升高、平滑项是否爆炸 | 视觉上脚掌是否贴地、动作是否像人 |
| `RUN_CONFIG.md` | 这个 run 到底用了哪个 CSV、哪组权重、尾部指标、有哪些 checkpoint | 自动判断视频质量；生成器明确把“训练结果”留给人工填写 |

不是只看总 reward。v5 总分高但乱飘，v1 mimic 分也不低但出生即倒。总 reward 会随着权重整体缩放，跨版本直接比较常常没有意义。

### 12.2 实际调参闭环

1. **先看回放并只定义一个主症状**：例如“后退”，不要同时把后退、勾脚、手臂幅度和腿抖一起改。
2. **定位负责该行为的最小奖励集合**：后退看 root 速度与位移；腿抖看腿 vel/acc；勾脚看踝和脚接触；跪姿看 base height/squat/upright gate。
3. **查 TensorBoard 的时间关系**：症状是在训练一开始就存在，还是 4k/6k 后策略找到捷径。后者说明奖励结构允许投机，不只是训练不足。
4. **打开该 run 的 `RUN_CONFIG.md`**：确认实际生效的 `env.yaml`，不要根据当前 `punch_env_cfg.py` 猜历史 run。
5. **一次只改一类问题并从 iter 0 重训**：奖励结构、观测目标、CSV 或 spawn 改变后，不用旧 checkpoint resume 来“省时间”。
6. **500–1000 iteration 做早期止损**：出生即倒、关键跟踪项从起点恒定、终止项极高时立即停止。
7. **选多个 checkpoint 看视频**：早期可能站得稳但动作小，晚期可能为了 mimic 学会碎步；最终 checkpoint 不天然最好。
8. **训练内通过后再做 Sim2Sim**：Isaac 视频验证策略，MuJoCo 验证观测/动作/物理对齐，两类问题不要混成奖励调参。

### 12.3 TensorBoard 的具体判读

- `track_punch_arms` 上升且视频手臂幅度同步增加：手臂跟踪在真正学习。
- `track_punch_arms` 高但视频跪地或倒地：检查是否缺 upright/height gate，属于刷分。
- `flat_orientation_l2`、`base_height` 接近零且终止下降：站立底座在改善。这里“接近零”是惩罚小，不是奖励失效。
- `action_rate_l2` 和 `action_smoothness_l2` 绝对值突然放大：动作开始高频抖动；v14 的异常大数就是典型信号。
- `penalty_root_xy_displacement` 越来越负且视频走远：位置锚定不够；若该项很小但仍后退，要检查 reset 原点、坐标和权重。
- `base_contact` 只适合同一 logger 口径下做相对比较。日志名虽写“终止率”，聚合值未必是严格百分比，出现大于 1 不能直接按百分数解释。
- 曲线从 step 0 就平直不等于收敛；若伴随出生即倒，是 episode 极短导致的坏解常数。

## 第十三章：RUN_CONFIG.md 如何生成、记录什么、为什么有用

### 13.1 自动生成链路

训练启动后，`scripts/rsl_rl/train.py` 先把解析后的配置写入：

- `params/env.yaml`
- `params/agent.yaml`
- `params/env.pkl`
- `params/agent.pkl`

随后 `_write_run_config("started")` 用当前 Python 解释器启动 `scripts/tools/write_run_config.py <run_dir> --status started`。训练正常结束后再次以 `completed` 生成；捕获到中断或异常时以 `interrupted` 生成后继续抛出异常。

生成器的处理逻辑是：

1. 从该 run 自身的 `params/env.yaml` 解析 CSV 路径、reward 函数、weight、`std`、门控阈值和高度目标。
2. 根据结构特征推断 v2/v9/v17/v18 等版本标签。这个标签是启发式摘要，不替代 `env.yaml` 真源。
3. 扫描 `model_*.pt`，记录最近 checkpoint。
4. 用 TensorBoard `EventAccumulator` 读取 `events.out.tfevents.*`。
5. 对指定 tag 的最后 10% 标量取均值，写入“最终收敛奖励值”。
6. 生成 run 根目录下的 `RUN_CONFIG.md`。

### 13.2 为什么不直接看当前 Python 配置

`punch_env_cfg.py` 会不断被下一轮实验覆盖。两周后再打开旧 run 时，当前文件已经是 v18，无法回答 v9 当时到底用了多重的脚约束。`params/env.yaml` 是运行时解析后的不可变快照，`RUN_CONFIG.md` 是它的可读摘要，因此解决了：

- 权重和视频对不上号；
- 不记得某 run 使用 S54、LAFAN1 还是 HYBRID CSV；
- 误把当前配置当成历史配置；
- 只凭 run 日期猜 reward 版本；
- checkpoint 很多但不知道哪次训练的收敛状态。

### 13.3 RUN_CONFIG 的边界

- “训练结果”必须看视频后人工填写；脚跟支撑、碎步、动作僵硬无法从标量可靠推断。
- 版本号是 `infer_reward_version()` 的规则推断。早期几个 run 被标成 v6/v7，而人工历史称 v1/v2/v8，遇到冲突应以 **run 日期 + env.yaml 实际权重** 为准。
- 尾部 10% 均值适合总结，不适合发现中途崩坏；完整走势仍看 TensorBoard。
- 脚本重跑会覆盖文件，因此人工视频结论若直接写在自动生成区可能丢失。需要长期保留时，应另建实验索引，或先改生成器支持持久化人工备注。

手动为单个或全部历史 run 重建：

```bash terminal
cd /home/lwy/Notes/kuavo-dev-notes/leju_robot_rl
python3 scripts/tools/write_run_config.py logs/rsl_rl/Kuavo/s49/dance/2026-07-17_05-51-49 --status completed
python3 scripts/tools/write_run_config.py --all-under logs/rsl_rl/Kuavo/s49/dance --status completed
```
